# استاندارد داکیومنت‌های Janebi Store

> **Status:** living · **Updated:** 2026-10-13 · **Scope:** کجا هر سند نوشته می‌شود، نام و سرِ سند آن چیست، چطور نوشته و نگه‌داری، بایگانی یا حذف می‌شود.

## ۱. سه اصل

1. **هر حقیقت در یک جا نوشته می‌شود.** سند دیگر لینک می‌دهد، کپی نمی‌کند.
2. **هر سند یک پرسش را جواب می‌دهد.** اگر دو سند یک پرسش را جواب می‌دهند، یکی را ادغام، بایگانی یا حذف کن.
3. **سند زنده وضعیت فعلی را می‌گوید.** تاریخچه به `docs/ledger/changelog-agent.md` یا `docs/archive/` می‌رود، نه داخل سند زنده.

## ۲. کجا بنویسیم

همه‌چیز زیر `docs/` است. دو فایل ریشه استثنای قراردادی‌اند چون GitHub و ابزارهای agent دنبال آن‌ها می‌گردند.

### استثناها (جای این فایل‌ها عمداً بیرون `docs/` است)

- `scripts/README.md`، `tests/README.md`، `bale-worker/README.md`: فهرست همان پوشه. کنار کدی می‌مانند که توضیح می‌دهند. شمارش تست فقط در `tests/README.md` است.
- `public/pricing.md`: محتوای عمومی سایت است و با URL `/pricing.md` سرو می‌شود. جابه‌جایی آن لینک‌های بیرونی و `llms.txt` را می‌شکند.
- `docs/reference/CATEGORY-TREE.md`: فهرست قفل‌شدهٔ دسته‌ها. نام و محتوایش فقط با تأیید صریح ادمین عوض می‌شود. `scripts/data/validate-ingest.py` و `scripts/oneoff/build-specs-plan.py` با مسیرش کار می‌کنند.
- `docs/data/specs-backfill-plan.json`: نامش را اسکریپت‌ها می‌خوانند.
- فایل‌های ابزار و محلی (ignored): `.serena/`، `.hermes/`، `memory/`، `IDENTITY.md`، `SOUL.md`، `USER.md`، `DREAMS.md`، `docs/shots/`. این‌ها مال ابزار یا محیط محلی‌اند و این استاندارد آن‌ها را مدیریت نمی‌کند.
- `docs/code-pro-hermes-guide.md` و `.pdf`: یادداشت شخصی و ignored. تا تصمیم کاربر دربارهٔ انتقال به بیرون repo، همان‌جا می‌ماند. چون ignored است، git آن را بازنمی‌گرداند؛ پیش از حذف باید پرسید.

## ۳. نام‌گذاری

- سند زنده در `docs/`: `<kebab-case>.md`، همه با حروف کوچک، بدون تاریخ در نام. استثنا: `docs/reference/CATEGORY-TREE.md`.
- گزارش و بایگانی: `<YYYY-MM-DD>-<kebab-case>.md`. تاریخ در نام، تاریخ **ثبت** یا **بایگانی** است؛ تاریخ داخل سند در هدرش می‌آید.
- نام فایل بعد از بایگانی عوض نمی‌شود، چون لینک‌های تاریخی به آن اشاره دارند.
- هر تغییر نام یا انتقال یک ردیف در جدول «مسیر قدیم → مسیر جدید» در `docs/README.md` می‌گیرد.

## ۴. سرِ سند

هر سند زنده و هر گزارش، بعد از عنوان `#` این خط را دارد:

```
> **Status:** living · **Updated:** YYYY-MM-DD · **Scope:** یک جمله
```

- **Status**: `living` (زنده و به‌روز می‌شود)، `frozen` (گزارش؛ بدنه دست نمی‌خورد)، `historical` (بایگانی‌شده)، `locked` (قفل).
- **Updated**: تاریخ آخرین تغییر محتوا. گزارش‌ها به‌جایش **Date** دارند: تاریخ گزارش.
- **Scope**: یک جمله که می‌گوید سند چه چیزی را پوشش می‌دهد و چه چیزی را نه.
- ledgerها (`docs/ledger/`، `docs/reference/project-graph.md`) به‌جای این خط، بلاک‌کوتِ «نقش» خودشان را دارند.

## ۵. نوشتن

- **زبان**: مرجع مهندسی انگلیسی یا فارسی؛ runbook و گزارش‌هایی که مالک کسب‌وکار می‌خواند فارسی. هدر و نام فایل همیشه انگلیسی.
- **شاهد**: هر ادعای وضعیت یک مسیر فایل، یک commit، یا یک تاریخ اندازه‌گیری دارد. «production ready» یا «live» بدون تاریخ تأیید ننویس. ادعاهای endpoint، نام env، نام تابع و عدد را با کد یا API زنده تطبیق بده، نه از حافظه.
- **عدد**: شمارش‌های متغیر فقط در یک جا: تعداد تست در `tests/README.md`، تعداد محصول از API زنده. بقیهٔ اسناد لینک می‌دهند.
- **تکرار نکن**: قبل از نوشتن، سند مالک (بخش ۶) را پیدا کن و همان‌جا به‌روز کن.
- **مسیر**: مسیرها از ریشهٔ repo و در code font، مثل `` `server/routes/cart.ts` ``. لینک Markdown نسبی به فایل سند باشد. مسیر مطلق مثل `/Users/...` ننویس.
- **دستور**: در بلاک `bash`، یک دستور در هر بلاک.
- **داده شخصی و امنیت**: هیچ secret، IP سرور، رمز، توکن، شمارهٔ کارت، شمارهٔ موبایل یا ایمیل شخص واقعی، و هیچ شناسهٔ ترمینال یا مرچنت درگاه. مقدار واقعی فقط در `.env` یا `deploy.env` محلی (ignored) می‌ماند. ریپو می‌تواند عمومی شود؛ هر چیزی که وارد git شود تاریخچه‌اش می‌ماند.
- **ادعای ناتمام**: آنچه تست یا تأیید نشده، در بخش `Limitations` یا `باز` بنویس، نه به‌عنوان واقعیت.

## ۷. چرخهٔ عمر

1. **ایجاد**: اول مالک را پیدا کن. اگر موضوع جدید است، فایل را در پوشهٔ درست با هدر بساز و در `docs/README.md` ثبت کن.
2. **به‌روزرسانی**: سند زنده را در جای خودش ویرایش کن و `Updated` را عوض کن. گزارش را بازنویسی نکن؛ بخش `## Update YYYY-MM-DD` به انتها اضافه کن.
3. **کار بسته شد**: آیتم را از `docs/ledger/tasks.md` به `docs/archive/` منتقل کن، بدون حذف، و در `docs/ledger/changelog-agent.md` ثبت کن.
4. **سند جایگزین شد**: به `docs/archive/<YYYY-MM-DD>-<slug>.md` ببرش، banner بگذار (`Status: historical · Superseded by …`) و ردیف جدول مسیرها را اضافه کن.
5. **حذف**: فقط وقتی همهٔ این شرط‌ها برقرار است: (الف) سند جایگزین دارد یا کد جایگزین آن است؛ (ب) محتوای یکتا ندارد، یا محتوای یکتایش در ledger یا سند دیگری آمده؛ (ج) هیچ سند زندهٔ دیگری به آن لینک نمی‌دهد؛ (د) داده شخصی یا ادعای نادرست ندارد. فایل tracked را git نگه می‌دارد؛ فایل ignored را هیچ‌وقت بدون پرسیدن حذف نکن.

## ۸. ledgerها

- `docs/ledger/tasks.md` فقط کار باز دارد. وقتی ورودی کاربر برسد، همان روز آیتم را ببند و منتقل کن.
- `docs/ledger/changelog-agent.md`: هر تغییر یک هدینگ `## YYYY-MM-DD — عنوان — وضعیت` دارد، جدیدترین بالا. همه هدینگ‌ها همین قالب را دارند.
- `docs/reference/project-graph.md` ساختار را نگه می‌دارد. بعد از تغییر ساختار، بخش مربوط را **در جای خودش** ویرایش کن و تاریخ تأییدش را عوض کن. روایت تغییرات اینجا نیست.
- ledgerهای append-only (`docs/ledger/changelog-agent.md` و `docs/reference/ui-audit-log.md`) خطوط قدیمی را که به مسیرهای قبلی اشاره دارند تغییر نمی‌دهند. نگاشت مسیرها در `docs/README.md` است.

## ۹. بررسی

```bash
node scripts/docs/check-links.mjs
```

این اسکریپت لینک‌ها و مسیرهای داخل backtick را در اسناد زنده بررسی می‌کند و حروف بزرگ و کوچک نام فایل را هم چک می‌کند، چون macOS آن را نادیده می‌گیرد اما CI لینوکسی نمی‌گیرد. `docs/reports/`، `docs/archive/` و ledgerهای append-only عمداً کنار گذاشته شده‌اند.

- مسیر قدیمی که **عمداً** باقی مانده (جدول انتقال، شاهد) با تگ کامنت HTML `link-check:ignore` در همان خط، یا با بلاک `link-check:off` … `link-check:on` علامت می‌خورد.
- در مثال‌ها جای نام را با `<…>` نشان بده، مثل `<YYYY-MM-DD>-<slug>.md`؛ این شکل‌ها مسیر حساب نمی‌شوند.
- این بررسی جزو `npm run verify` نیست؛ قبل از commit دستی اجرا کن.
